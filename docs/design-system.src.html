01

Direction

01

Design philosophy

The photography is the content. Everything else is scaffolding that should be felt and not noticed.

BTL's identity is unusually well resolved, and it is not the thin, quiet, luxury-serif language most architecture sites default to. The guide sets headers in Satoshi Black at 100% leading — heavy, tight, confident. It gives a signature device, the btl line, with hard rules about which colour it takes on which ground. It sanctions dark mode outright and mocks the website itself as a dark UI.

Four commitments follow:

  • Heavy type, quiet everything else. Display type is Black and tight. That is the one loud element. Around it: hairline rules, whitespace, no cards, no shadows, no gradients.
  • The line is the only ornament. Section breaks, margin rules, hover underlines, scroll progress. Nowhere else. An ornament used everywhere stops being one.
  • Photography is never boxed. No borders, no rounded corners, no drop shadows on any project image.
  • Restraint is structural. The system's job is to make a bad page hard to build.

Both reference sites agree. SCDA is a full-bleed photograph with an oversized wordmark and three links. BIG is a white page with a right-aligned title column beside each image and enormous vertical rhythm. Neither has a card, a shadow or a gradient anywhere.

02

Changes to the brief

Four deviations. The first is approved; the rest stand as decisions I have taken and would defend.

Hybrid structure, not a pure one-pager approved

A single page with anchor navigation gives search engines one URL, gives you nothing to share but the homepage, and leaves no room for a Journal or Awards. The home page keeps its scrolling narrative — every section present, reachable by scroll — but each section is a curated summary linking to a real page at a real URL. Nav on the home page scrolls; nav everywhere else navigates.

The carousel is replaced by a scroll-driven sequence decided

Content that moves on its own is hard to read, hard to operate by keyboard, and a known trigger for vestibular disorders. It also buries projects two through six — click-through past the first slide is consistently poor. Featured projects now arrive as you scroll: each takes the full viewport, the image revealing by mask, the title settling a beat later. Same drama, no accessibility debt, and every project gets seen because reaching the next one is the same gesture as reading.

Publications is a page from day one

Building it as a home section now and a page later means building it twice. Build the page now — the AD feature on Nelly House is already real content — and let the home page surface the two most recent items.

Instagram stays a link

A live grid means an access token that silently expires and a third-party script on every page load. The brief already says link, and the brief is right.

03

Theme strategy new

Recommendation: the site is dark by default and has no theme toggle. White is used as an editorial device, not as an alternative skin.

This was an unanswered question in the last draft and it affects nearly every other decision, so it is worth settling explicitly.

All projects

The practice

Both panels above are hardcoded, so they look identical no matter which theme you are reading this document in. Note the accent and the line obeying the ground rules from §13 without being told: cyan and green on dark, blue and red on white.

Why this document is not dark

You are most likely reading this on a white page, which looks like a contradiction. It is not. This document is a specification, not the site. It follows your system theme deliberately, so every token pairing in §13 can be checked on both grounds in one sitting — the swatches, the contrast figures and the accent rules all need to be verifiable in light and dark. The site has no such obligation and takes a position instead. If you want to see the document itself on dark, switch your OS appearance or use the viewer's theme toggle.

Why dark

  • The identity guide mocks the website itself as a dark UI, and devotes a page to "dark mode? we got that too." It is sanctioned, not tolerated.
  • Photography reads better against dark. Galleries and museums paint their walls dark for a reason: it removes the ground from competition with the image.
  • The accent system already has a dark answer — green and cyan — and those are the colours the guide pairs with black.
  • Nelly House's photography is warm, earthy and low-key. On white it looks washed; on near-black the terracotta and oxide tones hold.

Why no toggle

An architecture portfolio is art-directed. Letting a visitor invert it changes how every photograph reads, doubles the QA surface on every component forever, and adds a control to a navigation bar that should hold five items. Sites that need a toggle are tools people spend hours in. This is not that.

Where white is used

Deliberately, and as a change of register rather than a preference:

  • Studio and Journal — long-form reading, where a light ground is genuinely easier
  • Drawings — plans and sections are line work on white and must stay that way
  • Press — publication logos are supplied for light grounds
  • Any project block an editor sets to light ground

Reversible by design

Every token in Part four already has both values, and this document renders in both — use your OS setting or the viewer's toggle to see it. Flipping the site's default is a one-line change. Committing now costs nothing later; not committing means every component gets designed twice for no reason.

The site must not follow the OS setting new

A contradiction worth naming, because it is easy to build by accident. If the site is dark by design, it must not respond to prefers-color-scheme. Otherwise a visitor whose laptop is set to light gets a light site, and the art direction this section just argued for evaporates for half the audience.

So: the site ships one ground. The tokens keep both sets of values — that is what makes the decision reversible — but no media query selects between them at runtime. Light sections opt in explicitly with data-ground="light", which is an editorial choice made in the CMS, not a preference read from the device.

This document is the exception, and deliberately so: it is a specification and needs both grounds checkable in one sitting.

Implementation notes: color-scheme: dark so form controls and scrollbars follow, a theme-color meta of #050505 so mobile browser chrome matches, and the header reads data-ground off each section to invert its own contrast.

Growing into categories new

The practice has four projects. Splitting four projects across Residential, Apartment and Commercial gives three pages, two of them nearly empty — which makes a young practice look thinner than it is. But the categories are coming, and nobody wants a developer involved on the day they arrive.

So the filter bar is earned, not switched on. It appears by itself when the content justifies it, on a rule the CMS evaluates at build:

show the filter bar when
    ≥ 2 categories each hold ≥ 3 published projects
otherwise
    show every project, unfiltered, and no bar at all

Same for locations. Until then the index is simply all the work, which at four projects is the right answer anyway. The category routes are generated the whole time and carry their own metadata — they are just not linked from anywhere and are kept out of the sitemap until they hold enough to be worth landing on.

Nothing needs to be hidden, remembered or turned on. The studio adds its fifth Residential project and its third Commercial one, and the bar appears on the next publish. That is the answer to "can we hide it or something" — it hides and reveals itself, and no developer is involved either way.

Combined filters stay query parameters — ?place=wayanad — filtered client-side and canonicalised to the base page. Six categories times eight locations is several hundred near-identical pages with two projects each, which is thin-content generation that damages the pages that matter.

Slug stability

A slug is generated from the title on first save and locked at publish. If the title changes, the URL does not. If a slug genuinely must change, the editor adds a redirect and the old URL 301s permanently. Nothing breaks and no inbound link dies — which matters more now that AD has published a feature that may eventually link here.

06

Navigation

Five items, and they stay five: Projects · Studio · People · Press · Contact. No project types in the navigation — the index is one list, and it stays one list until §05's threshold is met.

The line belongs to the navigation, and only one at a time changed

A plain underline is what every site does. The btl line has an inflection in it, and at nav scale that inflection is legible — a small, specific mark that is unmistakably this practice. That is worth exactly one place on the screen.

Two things were tried and reverted, and both are worth recording because they are the obvious mistakes.

Putting the line on every link. Nav, inline links, footer links all wearing the inflection. Several curves visible at once stops reading as a signature and starts reading as noise. Ordinary links now take a plain 2.25px rule in the mark colour — same colour, same left-to-right reveal, no inflection. The device stays rare.

Letting two nav lines show at once. The current page held its line while a hovered item drew a second one beside it, and two of them side by side looked like a mistake rather than a state. The rule now: while the navigation is being hovered, the current page hands its line to whatever is under the cursor and takes it back on leave. Never more than one line in the bar.

It is drawn with markup, not a mask. A flat bar that stretches to the link width, plus the actual inflection vector at its natural aspect beside it. A CSS mask was tried and reverted: scaling the vector into a short box compressed the long rise into a tick, and it stopped being the supplied element. Markup keeps the curve's true proportions at any width. Revealed with clip-path rather than a horizontal scale, because scaling would squash it.

Header

  • Fixed, transparent, no background plate. Logo and links invert against the section behind them using an IntersectionObserver reading a data-ground attribute off each section — not a scroll handler measuring pixels.
  • On the home page links smooth-scroll and the active section is marked aria-current. Everywhere else they are ordinary links.
  • Padding shrinks after the hero. No hide-on-scroll: it is disorienting and it hides the only exit from a long project page.

Mobile

  • Full-screen overlay from a labelled button, not a bare icon. Focus trapped, Esc closes, scroll locked, focus returned on close. Drawn in §25.
  • Links set around 28px with 56px targets. Address and phone at the bottom — on a phone, calling the studio is a top-three action.

Within the work

  • Every project ends with previous / next in the same category, then back to index. Never a dead end.
  • Related projects are editor-chosen, falling back to same-category automatically when empty.
  • Breadcrumbs on project pages only, marked up as BreadcrumbList. Elsewhere they are noise.

The fact sheet is gone changed

Year, status, architects and area no longer appear on a project page. The client's instruction was blunt and correct — "all this info not needed" — and a table of five rows nobody reads is exactly the kind of thing that accumulates because a component exists to hold it. No scheduled publishing in v1 changed

An earlier draft implied that a future-dated publishedAt would go live on its own. On a statically generated site it will not — the build happened yesterday and nothing wakes it up on the date. Making that real needs a scheduled rebuild or a release webhook, which is machinery for a requirement nobody has stated. An architecture studio publishes when the photographs are ready, not to a timetable. The editor presses publish. If a genuine embargo comes up later, a nightly build is a small addition.

Rights is a publishing gate, not a checklist

An image whose rights is Unknown cannot be published — the CMS refuses, and the build fails if one reaches it. This is not bureaucracy: we already hit the problem. The eighteen Nelly House photographs came off AD's CDN and are licensed to Condé Nast, and AD credited nobody. A pre-launch checklist would not have caught that; a publishing constraint does. Alt text and rights are the two things the schema will not let an editor skip.

09

Project block system

A project is a fixed frame and an ordered sequence of slides. Five slide types, not nine blocks.

The previous draft specified nine block types for a vertically scrolling project page composed like an article. The page is no longer that. It is a title, one short text, and five or six photographs scrolled sideways — so most of those blocks had nothing to do. Keeping them would have meant an editor choosing between eleven options to build a page that has one shape.

The frame — identical on every project

TitleThe project name

Five slide types

Image

One photograph at its own aspect ratio. The workhorse — most slides are this.

Stacked pair

Two portraits sharing one slide width, one above the other.

Video

Poster required. Plays in place, or opens out.

Drawing

Plan or section. Light ground always, zoomable, never cropped.

Text interlude

A quote or a line of context, mid-sequence. Rare by design.

What the editor actually does

Drag in six photographs, set a focal point on each, type alt text, write one paragraph. That is the whole job. There is no page to compose, no layout to choose, no caption to write six times. The constraint is the design — every project comes out looking like the practice rather than like whoever built that page.

What this costs

Stated plainly: project pages can no longer be individually art-directed. A project that genuinely needs an essay, twenty drawings and a long photo essay cannot have one inside this system. That is the trade for an editor who never has to think about layout, and for a portfolio that stays coherent at thirty projects. If a monograph-style project ever becomes necessary, it is a new template — a deliberate piece of work, not a setting.

11

CMS approach

It is Sanity, with the schema versioned in the repository.

In plain terms: Sanity is a hosted editing app. You sign in on a web page, fill in fields, drag photographs in, hit publish, and the site rebuilds itself. The content lives on their servers; the design of the forms lives in our code, so we control exactly what an editor sees.

The deciding factor is images. The hard problem in an architecture portfolio is not storing photographs, it is cropping them. Sanity lets an editor click the important spot in a photograph once; every crop the site derives from it — wide hero, tall card, square thumbnail — keeps that spot in frame automatically. Without it, either someone hand-crops every image at every size forever, or heads get cut off on mobile.

Second: resizing happens on Sanity's servers when a visitor first asks for an image, not while the site is building. Adding five thousand photographs does not make deploys slower.

AlternativeWhy not
PayloadExcellent, but self-hosted: needs a database and a server the practice keeps running.
Keystatic / TinaFree, no vendor, content in the repo. But photographs in a git repository fail badly past a few hundred, and you would add Cloudinary anyway.
Contentful / StoryblokCapable; pricing escalates and block editing is less flexible than §09 needs.
WordPressMaintenance and security burden is real, and its editing model fights the block system.

The dependency, stated plainly

Sanity is a third party. If it vanished, content would need migrating. Mitigations: the schema is ours and lives in the repo; the whole dataset exports to documented JSON with one command; a monthly export runs to your own storage. The account is registered to BTL, not to me. The free tier covers a practice this size comfortably.

Two contrast findings

Brand red measures 4.1:1 on white as shipped — below the 4.5:1 minimum for body text. Blue measures 7.0:1. So blue is the interactive and text accent; red is the line device and large display moments only. This matches how the guide actually applies colour.

Crimson #BD1644 serves as the error colour on light grounds at 6.9:1, but is too dark on near-black. Dark mode uses a lightened #FF5C7A — derived, and the only colour in the system with no brand-book equivalent. Flagging it rather than quietly inventing it.

Ground rules, encoded rather than remembered:

  • On white → the line is red or blue
  • On a solid brand colour → the line is white
  • On dark → the line is green or cyan
  • On a photograph → treat it as a dark ground, whatever the page theme. Without this the hero cue turns red on a light page and vanishes into the foliage.
  • Violet, teal and crimson are background colours for occasional statement sections. Never text, never small elements.

Accessibility

WCAG 2.2 AA, built in from the first component.

  • Alt text is a required CMS field. The highest-leverage decision on the project — it makes the commonest failure impossible rather than unlikely.
  • Semantic HTML. Real landmarks, one h1 per page, headings in order. Block headings map to h2/h3 automatically so an editor cannot break the outline.
  • Keyboard. Everything operable in a logical order. Skip link. Focus trapped in the mobile nav and lightbox, returned to the trigger on close.

  • Contrast. Every pairing in §13 measured and listed; brand red restricted, error colour lightened for dark ground.

  • No auto-advancing carousel — removed rather than mitigated.
  • Forms — real labels, errors in text linked to the field, announced politely, never colour alone. §21.
  • Icons — hidden from assistive technology when decorative, labelled when alone. §18.

Version policy

An earlier draft of this document said "Astro 5", which was two majors stale by the time it was written. That is precisely the failure this rule exists to prevent: pin the latest stable major at project start, lock exact versions in the lockfile, never cross a major version automatically. Confirm the current release on day one rather than trusting a number in a document written weeks earlier — including this one. A major upgrade is deliberate work with a review, not a dependency bump.

Escape hatch

Astro can switch individual routes to on-demand rendering without restructuring anything. If builds ever exceed about three minutes, /projects/[slug] flips to on-demand with CDN caching.

What is holding up
